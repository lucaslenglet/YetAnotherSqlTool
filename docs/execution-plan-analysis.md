# Execution plan: pre-analysis

Status: not started. This is a sizing of the work, written before any code, to pick the
feature up later. Step 1 (SQL Server) is the only one studied in detail.

References read (local clones kept outside the project, read-only):
- vscode-mssql, commit `fa3aee0` (the project's upstream reference, see
  `vscode-mssql-analysis.md`). Paths below are relative to `extensions/mssql/src/`.
- sqltoolsservice, commit `868e069`. Paths relative to
  `src/Microsoft.SqlTools.ServiceLayer/`. The clone is a sparse checkout limited to
  `QueryExecution/`: read the other folders with `git show HEAD:<path>`.

## Planned steps

1. **SQL Server**: estimated plan and actual plan, shown in Microsoft's page.
2. **PostgreSQL**: `EXPLAIN (FORMAT JSON)` (`ANALYZE` for the actual plan) converted to the
   same graph shape, so the same page displays it. PostgreSQL operators (Seq Scan, Hash
   Join...) need a mapping to the existing icons. `EXPLAIN ANALYZE` really runs the
   statement: an `UPDATE` / `DELETE` changes data (as with Microsoft's actual plan), so warn
   or wrap it in a transaction that is rolled back.
3. **Later**: open / save `.sqlplan` files, compare two plans.

`ExecutionPlanService` only sends `queryExecutionPlan/getExecutionPlan` with
`{ graphInfo: { graphFileContent: <XML>, graphFileType } }` to sqltoolsservice and gets back
`ExecutionPlanGraph[]` (nodes with costs, properties, badges, edges, missing index
recommendations). YAST keeps that contract and replaces the request with a TypeScript
converter, so the rest of Microsoft's code stays close to upstream.

Some leftovers of the removed feature are already in YAST: `cmdCompareExecutionPlans`,
`queryPlanXmlStart`, `showPlanXmlColumnName` in `src/constants/constants.ts`, strings in
`src/constants/locConstants.ts`, `ExecutionPlan` in `src/sharedInterfaces/telemetry.ts`.

Running the query: sqltoolsservice (`QueryExecution/Query.cs`) wraps the batch with
`SET SHOWPLAN_XML ON|OFF` (estimated) or `SET STATISTICS XML ON|OFF` (actual). The plan
comes back as a result set whose single column is named
`Microsoft SQL Server 2005 XML Showplan`. Upstream commands toggle the actual plan per editor
(context key `mssql.executionPlan.urisWithActualPlanEnabled`, see `package.json`).

## sqltoolsservice side: the real work

`ExecutionPlan/` is about 22,000 lines, but most of it is not to be ported:
- `ShowPlan/showplanxml.cs` (13,141 lines) is generated by `xsd.exe` from
  `ShowPlan/showplanxml.xsd` (2,483 lines). We read the XML directly instead.
- About **6,000 lines of real logic**, among which:
  - `ShowPlan/PropertyFactory.cs` (787): the displayed properties, with display order,
    tooltip visibility and "better value" direction, each with a localized name and
    description (~175 `SR.*` keys, from `Localization/sr.strings`).
  - `ShowPlan/ObjectWrapperTypeConverter.cs` (1,111): value formatting (sizes, floats,
    nested objects). Built on .NET reflection (`TypeDescriptor`): to be rewritten rather
    than translated line by line.
  - `ShowPlan/RelOpTypeParser.cs` (732), `OperationTable.cs` (404, operators → icons),
    `Node.cs` (770), `XmlPlanNodeBuilder.cs` (495), `XmlPlanParser.cs` (283),
    `ExecutionPlanGraphUtils.cs` (557, conversion to the contract and recommendations):
    walking the operators, costs, icons, badges.
  - `ShowPlan/Comparison/` (~340): step 3 only.

The code is MIT: port it keeping the Microsoft copyright header.

## How to check fidelity

Same method as "Script as" and the Object Explorer tree:
- write a `tools/sts-plan-probe.js` that records sqltoolsservice's `getExecutionPlan` output
  for a set of queries (joins, aggregates, missing index, parallelism, actual plan, several
  statements) into `docs/reference/mssql-execution-plans.json`, with the input XML;
- unit tests replay the XML through the TypeScript converter and compare with the capture;
- sqltoolsservice's own fixtures can be reused:
  `test/Microsoft.SqlTools.ServiceLayer.UnitTests/ShowPlan/TestShowPlan.xml` and
  `TestShowPlanRecommendations.xml`.

## Estimate for step 1

A feature the size of the Object Explorer, delivered in 2 or 3 PRs:
1. the probe and the reference captures (small);
2. the XML → `ExecutionPlanGraph` converter in `src/drivers/mssql/`, probably 2,000 to 3,000
   lines of TypeScript plus the localized strings (the big part);
3. the commands (estimated plan, toggle actual plan), the `SET` options in the query runner,
   the results tab and the page.

Open question: where the converter lives in the `Driver` interface (for example an optional
`executionPlan` capability), so that step 2 plugs PostgreSQL in the same way.
